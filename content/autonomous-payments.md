# Autonomous payments are not the same as recurring payments

A recurring payment repeats an arrangement. An autonomous payment can follow a decision made by software within permission you have granted. Both can happen without you clicking a button at the exact moment money moves, but they give software different kinds of responsibility.

That difference matters when you ask an agent to search for something and act. The agent may be choosing a candidate rather than paying the same known bill again. Its freedom to choose should be narrower than a vague instruction to do whatever seems useful.

## A subscription has a familiar pattern

With a subscription, you usually know the service and the billing arrangement in advance. The amount may vary under the terms, but the relationship is established. The software is mostly carrying out that arrangement.

An agent searching X for a meme coin is doing something different. It is looking through information, interpreting a request, and proposing a candidate. There may be no acceptable result. The ability to stop without spending is therefore part of the task, not an error to work around.

If the request says “spend up to $100,” that should not quietly become a recurring $100 allowance. A task ceiling and an ongoing arrangement are different forms of permission.

## Autonomy has more than one level

An assistant can research only. It can prepare an action for approval. Or it can act within a previously approved scope. Those are distinct experiences, even if each is described as autonomous in marketing.

Before using a product, look for which level applies to the action you are taking. Does pressing the main button start a search, configure permission, or submit a transaction? If the interface combines steps, its status and explanation should still make the outcome clear.

The [Veyro demo](https://tryveyro.casa) places the agent instruction and spend limit together. Read its displayed result rather than assuming that an interesting candidate means a purchase has completed. Our [result guide](/guides/understanding-agent-results) explains the distinction.

## Time limits make a difference

Permission that made sense this morning may not make sense next week. A short-lived task can use a defined end point: finish the search, complete one permitted action, or stop when the permission expires.

An ongoing task needs additional decisions. When does the allowance renew? Can an unused amount carry forward? Who can change the limit? Those questions are unnecessary complexity for a one-off search, so a product should not introduce them unless the user is actually asking for ongoing behavior.

For a simple task, the clearest arrangement is usually one goal, one visible ceiling, and an understandable stopping point. See [when agent permission should end](/guides/agent-permission-expiry).

## A failed response is not a new instruction

Automation also changes how retries behave. If a screen stops updating, clicking again can create confusion about whether the first action is still pending. A reliable system should preserve the connection to the original task and resolve its status.

As a user, avoid interpreting a slow response as proof that nothing happened. Check the current result or transaction reference before starting a new request. A second instruction can be a second task, even when your intention was only to refresh the first one.

## What to ask before delegating

You should be able to tell what the agent may choose, what it may spend, and when its authority ends. Those answers do not need to fill a technical settings page. They can be expressed in ordinary language beside the action.

Autonomous payments are useful when software can make a bounded choice you do not want to manage step by step. They become confusing when a one-time request is treated like an open-ended arrangement. Keep the scope visible, and judge the experience by whether it follows the task you actually gave it.
